## 1. VERSION GATING MECHANICS

### 1.1 The three gating layers (how AME Wizard playbooks gate versions)

**Layer 1 — `playbook.conf` `<SupportedBuilds>` (hard gate, exact match).**
- Atlas (`src/playbook/playbook.conf` lines 15–20): `26100` (24H2), `26200` (25H2) — nothing else. `AllowUnsupportedUpgrades=false`, `UpgradableFrom 0.4.1`.
- ReviOS (`/home/z/my-project/repos/revi-playbook/src/playbook.conf`): `19044, 19045, 22631, 26100, 26200, 26300, 28000`; `UpgradableFrom: any`; **no UCPDDisabled requirement**; Defender-disable is the *default* radio (opposite of Atlas).
- Engine enforcement (`trusted-uninstaller/TrustedUninstaller.Shared/Requirements.cs`, class `WindowsBuild`): `builds.Any(x => x.Equals(Win32.SystemInfoEx.WindowsVersion.BuildNumber))` — **exact string equality of the build number, no ranges, no UBR matching**. A playbook listing `26100` will not run on 26200 or 26300.
- User-visible UX on unsupported build: AME Wizard shows **"Requirements not met … This Windows build is not supported by this Playbook."** and refuses to continue — Atlas docs page + screenshot alt-text: https://docs.atlasos.net/faq/install-faq/ame-wizard-errors/build-not-supported/ (source repo `Atlas-OS/docs`, cloned to `/home/z/my-project/repos/atlas-docs`). There is no bypass button in the UI for end users.

**Layer 2 — per-task `builds:` filters in YAML (soft, range-based).**
Engine (`AmeliorationUtil.cs` `IsApplicable`, lines 115–129) evaluates per-file/per-action `builds:` lists with range and exclusion syntax; Atlas uses e.g. `builds: ['>=22000']` (Win11-only tweaks) and `builds: ['<22000']` in `Configuration/tweaks/qol/...`. This is how a playbook can support several builds in one `.apbx` while applying build-specific tweaks.

**Layer 3 — `<Requirements>` (environment preconditions).** Full enum in engine `Requirements.cs` (13 values): Internet, NoInternet, DefenderDisabled, DefenderToggled, NoPendingUpdates, Activation, NoAntivirus, LocalAccounts/PasswordSet, AdministratorPasswordSet, PluggedIn, NoTweakware, FreshInstall, **UCPDDisabled**. Official descriptions: https://docs.amelabs.net/developers/requirements.html (e.g. *"UCPDDisabled — Requires the user to disable the UCPD driver via the Prepare System step"*; *"DefenderToggled — Requires the user to toggle the primary four Windows Security toggles"*; NoAntivirus checks WMI `root/SecurityCenter2` `AntivirusProduct`; FreshInstall = install < 40h old, "easily bypassable in the UI").

**Dev-build bypass (how Atlas itself tests on any build):** `src/dependencies/local-build.ps1` flag `-Removals WinverRequirement` deletes every `<string>`, `<SupportedBuilds>`, `</SupportedBuilds>` line from `playbook.conf` (lines 110–121) so the built `.apbx` runs on any Windows. Other removals: `Verification` (strips `<ProductCode>` signature check), `Requirements` (strips `<Requirement>`s — comment notes AME Wizard 0.6.5 crashes if the `Requirements` *field* is missing entirely, so only items are removed), `Dependencies` (cuts the `NO LOCAL BUILD` block out of `start.yml`). CI (`​.github/workflows/apbx.yaml`) builds the release `.apbx` (password `malte`).

### 1.2 Upgrade gating
- `UpgradableFrom` formats (engine `Playbook.cs` `IsUpgradeApplicable` + https://docs.amelabs.net/developers/upgrades.html): single version `1.0.0`, range `1.0.0-2.0.0`, `any`, or multiple `<string>` entries. Invalid values throw `XmlException` at playbook load.
- `<AllowUnsupportedUpgrades>` (engine default **true**, `Playbook.cs` line 235): when `false` (Atlas sets this), the wizard blocks upgrades from playbook versions not listed in `UpgradableFrom` — per amelabs docs: "To prevent users from upgrading from an unsupported version that’s not specified in UpgradableFrom … `<AllowUnsupportedUpgrades>False</AllowUnsupportedUpgrades>`".
- Option carry-over during upgrade (amelabs upgrades doc): if an option existed in the old version and the user did **not** select it, its `onUpgrade` actions won't fire; new options (absent in old version) always fire.

### 1.3 What ReviOS does differently
ReviOS gates *loosely*: 7 builds including Win10, `UpgradableFrom: any`, no UCPD requirement, no `AllowUnsupportedUpgrades` (engine default true applies). Their tweaks branch at runtime on build (`FINALIZE.cmd`: `if %build% gtr 19045 set "w11=true"`). README (https://github.com/MeetRevision/playbook): "Any other build **is not** supported by Revision." — i.e. same hard gate, wider list. **ReviOS has already added `26300` (26H2) to SupportedBuilds; Atlas has not.**

### 1.4 The 26H2 fact UltraOS is built on (verified)
**Windows 11 26H2 = Build 26300** — release to Release Preview announced 2026-08-27 as **Build 26300.9278** (blogs.windows.com "Releasing Windows 11, version 26H2 to the Release Preview", https://blogs.windows.com/windows-insider/ ; corroborated by askwoody.com 2026-08-27 "Windows 11 Insider Preview build 26300.9278 (26H2)" and learn.microsoft.com 2026-06-19 "Windows 11 Insider Experimental Preview Build 26300.8697"; Microsoft maintains a "Windows 11, version 26H2 update history" page, support.microsoft.com, seen 2026-09-22). These pages are Cloudflare-gated to curl; cited from search-result titles/snippets — ⚠️ exact GA KB number not captured here (T1-d's dossier should pin it).
- Atlas gap: open feature request **Atlas-OS/Atlas #1739 "[FEATURE] Support for Windows 26H2"** (https://github.com/Atlas-OS/Atlas/issues/1739). Community comments state 26H2 support was announced on the Atlas Discord but users are told to "stick with Windows 11 25H2 for now" — i.e. **Atlas 26H2 support announced, not shipped**, as of 2026-10-07. UltraOS's opportunity window is real but likely short.

### 2.2 Store / AppX / Copilot reappearing & renames

- **Copilot disable on Atlas is a toggle, not removal**: `AtlasDesktop/3. General Configuration/AI Features/Microsoft Copilot/Disable Microsoft Copilot (default).cmd` — UWP app removal reserved for appx.yml `Microsoft.Copilot*`.

## 3. UCPD DEEP-DIVE

### 3.1 What UCPD actually is (correction to prior assumptions)
**UCPD = UserChoice Protection Driver (`UCPD.sys`)** — *not* "Update Control Policies." It is a kernel registry-filter driver whose job is to protect **user file/protocol association choices (UserChoice keys) — primarily the default browser** — from programmatic hijacking. The mission brief's "Update Control Policies protection" framing is inaccurate; verified facts:
- **First shipped Aug 2023** in Win11 22H2 preview **KB5029351** (v1.0.1.383513, 29 KB, 58 functions) — 7 months before public discovery; broad activation/rollout began early 2024, public discovery ~Feb 2024 (the Win10 January 23, 2024 preview **KB5034203**, OS build 19045.3996, is the update associated with the rollout; https://support.microsoft.com/en-us/topic/january-23-2024-kb5034203-os-build-19045-3996-preview-… — DDG-indexed; ⚠️ exact KB support-page URL not curl-captured).
- **Protected paths (v1.0 strings)**: `HKCU\Software\Microsoft\Windows\Shell\Associations\UrlAssociations\http\UserChoice`, `…\https\UserChoice`; deny-listed processes: `reg.exe`, `powershell.exe`, `rundll32.exe`, `dllhost.exe`, `svchost.exe` (matched by name/original filename); only the Settings app may write.
- **Evolution (38 binaries, 24 versions analyzed)**: v2.0 added `.pdf\UserChoice` + `Control Panel\DeviceRegion`; v3.0 added process/publisher classification (Kingsoft, Qihoo/360, Edge, Explorer, Opera), object callbacks vs injection into trusted processes, UI-Automation defense; grew to **196 KB** "registry and process policy engine"; **v4.4–4.7 added cross-device resume, gaming (default gaming experience), FeatureV3, expanded deny list**. By 2026 it is "a region- and feature-dependent kernel policy engine that watches registry operations, process creation, loaded images, object handles, UI Automation, publishers, original filenames, and stacks — and can consume signed policy from the registry."
  - Sources: Xusheng Li, "How Windows UCPD Grew from a 29 KB Registry Filter into a 196 KB Policy Engine" (https://xusheng.dev/posts/reversing/ucpd_evolution/main/); Binary Ninja blog 2026-08-04, "The Binary Hiding in Your Registry: Cracking Windows UCPD's Dynamic Rules" (https://binary.ninja/2026/08/04/ucpd-dynamic-rules.html) — documents dynamic config PE stored under `HKLM\SYSTEM\CurrentControlSet\Services\UCPD\DR`; Christoph Kolbicz's original UCPD.sys research (https://kolbi.cz/blog/2024/04/03/userchoice-protection-driver-ucpd-sys/ — Cloudflare-gated, existence verified; content via xusheng's citations). Gunnar Haslinger's early-2024 write-ups co-credited by xusheng.
- ⚠️ UNVERIFIED (page 404'd on fetch): a KB article "User choice protection driver (UCPD) causing Explorer or icon flickering" (kb.powersyncpro.com, DDG-indexed) suggesting UCPD activity can cause Explorer/icon flicker on some systems.

### 3.2 Why Atlas *requires* UCPDDisabled (the real reason)
The Atlas playbook **programmatically sets file associations and default browser** for every user hive: `Executables/FILEASSOC.cmd` + `ASSOC.ps1` implement the UserChoice hash algorithm (`Get-Hash ext+SID+ProgId+timestamp+UserExperience` → write `Hash`/`ProgId` under `UrlAssociations\…\UserChoice` and `FileExts\…\UserChoice`), including offline `AME_UserHive_*` hives. UCPD blocks exactly these writes from PowerShell. Evidence: `FILEASSOC.cmd` lines 44–50 contain the comment **"Make a temporary renamed PowerShell executable to bypass UCPD"** (copies `powershell.exe` to `powershell<random>.exe` — defeating UCPD's process-name matching), citing https://hitco.at/blog/windows-userchoice-protection-driver-ucpd/. Even with that bypass, Atlas belt-and-braces: (a) declares `<Requirement>UCPDDisabled</Requirement>` in playbook.conf; (b) disables the UCPD service in `services.yml` (`UCPD` startup 4, labeled "Microsoft recommendation - No guidance" per MS IoT docs); (c) disables the **`\Microsoft\Windows\AppxDeploymentClient\UCPD velocity`** scheduled task (`disable-scheduled-tasks.yml` line 9, `ignoreErrors: true`, comment "might not exist on all installs") — this task re-enables/updates UCPD after servicing.

### 3.3 How the requirement is enforced & satisfied (wizard mechanics)
- Engine check (`Requirements.cs` `UCPDDisabled.IsMet()`): reads `HKLM\SYSTEM\CurrentControlSet\Services\UCPD` value `Start`; **met iff `Start == 4` (disabled) or the key is absent**.
- If unmet, AME Wizard runs its **"Prepare System"** step (`trusted-uninstaller` `Defender.cs` `DisableUCPD`, `CLI.cs` lines 102–150): disables the `UCPD velocity` scheduled task → sets `HKLM\SYSTEM\CurrentControlSet\Services\UCPD /v Start /d 4` via RegistryValueAction; **if ACL-blocked, falls back to `NSudoLC.exe` (TrustedInstaller) `reg add`** → informs user "The system must be prepared before continuing. Your system will restart after preparation" → **reboots** (driver unload requires reboot) → user re-runs playbook, requirement now met.
- ReviOS playbook does **not** use the UCPDDisabled requirement (their playbook.conf) — they don't hard-set associations during install (browser packages carry `DefaultWebBrowser="true"` in `<Software>` and the wizard's `CheckDefaultBrowser` flow handles user choice), so UCPD can stay enabled. **UltraOS design decision: either (a) Atlas-style UCPD-off + ASSOC.ps1 hash writes, or (b) Revi-style leave-UCPD-on and skip programmatic association changes.**

### 3.4 Risks both ways (for the UltraOS dossier's security section)
- **Leaving UCPD enabled while UltraOS writes associations**: writes silently rejected → defaults revert to Edge/defaults → user-visible bug reports ("my default browser reset"), exactly the class UCPD exists to cause for tools.
- **Disabling UCPD**: removes kernel-level protection against default-browser/file-type hijacking by malware (a real Windows hardening feature since 2023/2024); accept and document. Safe disable recipe (from engine code): disable velocity task → `Start=4` (use TrustedInstaller `NSudoLC` if access denied) → reboot. Re-enabling: `sc config UCPD start= auto` + reboot (⚠️ unverified exact default start type — likely `3` (manual) on 24H2+; verify on 26300 before shipping docs).
- **State on 26H2**: UCPD is still present and heavier than ever (dynamic-rules PE policy engine, gaming-experience protection per xusheng/binary.ninja 2026 research). T1-d's `windows-26h2-analysis.md` was **not present** at research time — flag for follow-up.

## 4. EDGE REMOVAL ON RECENT BUILDS (24H2/25H2/26H2)

### 4.1 Current working methods (verified 2026-10-07)
1. **Atlas's shipped tool** — `AtlasDesktop/1. Software/Install or Remove Edge.cmd` → wrapper for `AtlasModules\Scripts\ScriptWrappers\RemoveEdge.ps1` **v1.9.5** (derived from he3als/EdgeRemover, license note CC0 via ShadowWhisperer):
   - **Uninstall**: downloads latest `Remove-Edge.exe` from **https://github.com/ShadowWhisperer/Remove-MS-Edge/releases/latest/download/Remove-Edge.exe** and runs hidden. Philosophy (he3als README): "Remove Edge with its own uninstaller, meaning there aren't leftovers, alongside no breakage as nothing is hardcoded" + "Multiple fallback methods" + handles Edge installed via `.msi`.
   - **Reinstall Edge**: queries **https://edgeupdates.microsoft.com/api/products** (Stable, arch x64/arm64/x86), verifies SHA-256 hash, `msiexec /i` then `/fa` repair, parses MSI log for success string.
   - **Reinstall WebView2**: Evergreen bootstrapper `https://go.microsoft.com/fwlink/p/?LinkId=2124703` with `/silent /install`.
   - TUI options: [1] Uninstall [2] Install Edge [3] Install WebView [4] Both; params `-UninstallEdge -InstallEdge -InstallWebView -RemoveEdgeData -KeepAppX -NonInteractive`. Refuses to run as SYSTEM/TrustedInstaller (reg-blocks). Detects legacy UWP Edge (`SystemApps\Microsoft.MicrosoftEdge_8wekyb3d8bbwe`).
2. **ShadowWhisperer/Remove-MS-Edge** (the upstream): **actively maintained — last commit 2026-09-25**; 5,511 stars; CC0-1.0; batch trio: `Both` (Edge + WebView2), `Edge` (Chromium + Appx Edge only), `Edge-Appx` (packaged Edge only). Status verified via GitHub atom feed + hysenlabs project page "remove-ms-edge: browser or web view, pick one" (https://hysenlabs.com/projects/shadowwhisperer-remove-ms-edge, updated 2026-09-23).
3. **Community alternates**: he3als/EdgeRemover standalone (https://github.com/he3als/EdgeRemover, last commit 2025-06-13 — v1.9.5 era); AveYo gist EdgeUninstallGuide (https://gist.github.com/ave9858/c3451d9f452389ac7607c99d45edecc6).

### 4.2 What breaks when Edge/WebView2 is removed (documented dependency list)
- **WebView2-dependent apps** (15 listed by Remove-MS-Edge README): Xbox App, Windows Mail, Roblox, PowerToys File Explorer add-ons, Microsoft Photos (edit), Eclipse IDEs, ImageGlass 9, Tauri-based apps, Quicken, Safing Portmaster, Rex Atmos (MSFS 2020), Garry's Mod publisher, Barracuda Firewall Admin, Lenovo USB Recovery Creator.
- **Widgets** (needs Edge/WebView2; Atlas ships Widgets enable script that "installs Edge despite declining" — bug #1091 shows the coupling), **OOBE/search HTML surfaces**, anything MSHTML/WebView-hosted (Widgets, Outlook "new", Teams features).
- **Windows Update failure loops** (see §2.1) — the single most user-hostile failure.
- **EdgeUpdater scheduled tasks/services respawn** (#1631): remove `MicrosoftEdgeUpdateTaskMachineCore/UA` tasks + `edgeupdate`/`edgeupdatem` services or they recreate after reboot.
- **DMA-era changes**: Microsoft Q&A thread "Cannot delete MS Edge after the DMA changes" (https://learn.microsoft.com/en-us/answers/…, 2024-03-27) and Ghacks "Microsoft Removes 'How to Uninstall Edge' Page After DMA Changes" (https://www.ghacks.net/2025/02/11/… — title via search index) indicate Microsoft legally must allow EU-browser-default workflows but keeps tightening programmatic removal — expect breakage on new builds; that's why Atlas fetches Remove-Edge.exe from a **latest release URL** instead of vendoring it.
- Historical Atlas bugs: Edge wasn't removed (#1153, #1317 "got patched again"), cannot uninstall via script on Win10 (#1392), Edge loses functionality/rounded corners when kept but neutered (#980), Chrome sync pausing (1105), default-browser + .url assoc not switched when installing new browser (#1074 — handled by FILEASSOC.cmd).

### 4.3 Reinstall paths (all verified in Atlas's script)
Edge (via edgeupdates API MSI), WebView2 (Evergreen link), or `winget install Microsoft.Edge` ⚠️ UNVERIFIED for offline scenarios. UltraOS guidance: ship an "Install or Remove Edge" equivalent that always offers WebView2-only install, and never delete Edge user data by default (`-RemoveEdgeData` separate).

## 5. DEFENDER TOGGLING (Atlas method + tamper protection + consequences)

### 5.1 How Atlas toggles Defender (component-level, not registry hacks)
- Playbook default: **Defender ENABLED (recommended)** radio (`defender-enable`), docs page https://docs.atlasos.net/getting-started/post-installation/atlas-folder/security/#defender.
- Post-install toggle: `AtlasDesktop/7. Security/Defender/Toggle Defender.cmd` (runs as TrustedInstaller via `RunAsTI.cmd`) → `ToggleDefender.ps1` → **DISM-ads a removal CAB**: `Z-Atlas-NoDefender-Package31bf3856ad364e35[amd64|arm64]5.0.0.0.cab` (in `AtlasModules/Packages/`). "Enable" = DISM-remove the package. The CAB is generated by **sxsc** from `src/sxsc/Atlas-Defender-Remover.yaml`, which lists the Windows components to strip: `Security-Malware-Windows-Defender`, `Windows-Defender-AM-Default-Definitions-Deployment`, `Windows-Defender-AM-Engine`, `Windows-Defender-AM-Sigs`, `Windows-Defender-Branding(±Resources)`, `Windows-Defender-ApplicationGuard-Inbox-*`, `Windows-Defender-Events`, `Windows-Defender-Group-Policy(±…)`, `Windows-Defender-Management-MDM/Onecore`, `Windows-Defender-Drivers-NisDrvWfpEtw` (WdNisDrv network-inspection driver), `Microsoft-OneCore-WebThreatDefense-*` etc. (+ separate `Z-Atlas-NoTelemetry-Package`).
- **Install-time requirement `DefenderToggled`**: the user must turn off the **primary four Windows Security toggles** (real-time protection, cloud-delivered protection, automatic sample submission, **Tamper Protection**) before the playbook runs. Engine `Requirements.cs` `DefenderToggled.IsMet()` reads `HKLM\SOFTWARE\Microsoft\Windows Defender`: fails if `Real-Time Protection\DisableRealtimeMonitoring != 1`, `SpyNet\SpyNetReporting != 0`, `SpyNet\SubmitSamplesConsent != 0`, or `Features\TamperProtection != 4`. The CLI prompts: "All 4 windows security toggles must be set to off. Navigate to Windows Security > Virus & threat detection > manage settings." (`CLI.cs` lines 104–150).
- **Wizard "Prepare System" for DefenderDisabled playbooks** (engine `Defender.KillAndDisable`): disable UCPD → extract CAB → import its Authenticode cert to LocalMachine\Root (+ pinned thumbprint copy) → `DISM /Online /Add-Package /IgnoreCheck`; **if live DISM fails: install an `AMEPrepare` boot service (whitelisted under `SafeBoot\Minimal`), `bcdedit /set {current} safeboot minimal`, reboot into Safe Mode to remove Defender offline**, then disable safeboot. `dontdisplaylastusername=1` is set so the user can log in during this flow.

### 5.2 Tamper Protection interactions (why registry-only toggles fail)
With Tamper Protection ON, writes to Defender policy keys are protected even from admin/TrustedInstaller in many cases — hence the requirement that the *user* flip toggles in the UI before install, and hence DISM-package removal rather than `DisableAntiSpyware` registry games (which Microsoft long neutralized). The four-toggle checklist is the ecosystem's standard gate; UltraOS must replicate it if Defender will be touched at all. Also note `MpDefenderCoreService` process (new-ish Defender core service) appears in the engine's `DefenderDisabled` check (`!Process.GetProcessesByName("MsMpEng") && !SecurityHealthService && !MpDefenderCoreService`).

## 7. PLAYBOOK UPDATE MECHANICS (how Atlas ships updates; what survives)

### 7.1 Shipping updates
- **Distribution = Git releases** (amelabs docs https://docs.amelabs.net/developers/updates.html): release **Tag must equal `playbook.conf` `<Version>`**, release must contain **exactly one `.apbx`**; wizard polls the `<Git>` repo's releases API (GitHub/GitLab/Gitea — engine `Playbook.LatestPlaybookVersion()` hits `api.github.com/repos/<repo>/releases` with a curl UA) and offers the update. `.apbx` = password-protected ZIP (`malte`).
- Atlas versions: v0.4.1 (24H2) → **v0.5.0** current (24H2+25H2), `UpgradableFrom 0.4.1`, `AllowUnsupportedUpgrades false`. Version also baked into OEM info at build time (`AtlasVersionUndefined` placeholder replaced by local-build.ps1).

### 7.2 Upgrade mechanics (`onUpgrade` semantics — from engine source `AmeliorationUtil.IsApplicable`)
- **Fresh install**: actions with `onUpgrade: true` are skipped; everything else runs.
- **Upgrade to a newer playbook version**: `onUpgrade: true` actions run, `onUpgrade: false` skipped. Per-action `onUpgradeVersions: ['1.0', '>=1.0', '!1.2']` adds version conditions (requires `onUpgrade` defined, else YamlException).
- **Same-version re-run**: only `onUpgrade: false` actions whose gating option was *not previously applied* run (engine lines 94–97: same version → `return !onUpgrade.Value && !isApplicable`; i.e. idempotent "repair/extend" mode — amelabs docs describe this as re-application behavior).
- Atlas file strategy: `appx.yml`, `services.yml`, `components.yml`, `start.yml`, `script-pfp.yml`, `config-pins.yml` → `onUpgrade: false` (destructive/one-shot actions never re-run on upgrade); `revert.yml` → **`onUpgrade: true`** ("Reverts changes from past versions", referencing #1283 folder-hiding fix); selected atlas-theme/default.yml actions `onUpgrade: true`.
- **User flow** (Atlas docs https://docs.atlasos.net/getting-started/upgrade/upgrade-playbook/): download new `.apbx` → drag into AME Wizard → **choose "Upgrade" (not "Run again")** → "AME Wizard will analyze the current installation and apply only the changes required" → reboot. Known limitation: 0.4→0.5 upgrade did not carry over Atlas-folder configuration (documented; re-apply toggles). Systems on 0.3.x must clean-install; 0.3.x is legacy/unsupported. Applied-playbook state persists in `HKLM\SOFTWARE\AME\Playbooks\Applied` (UniqueId, Version, SelectedOptions, AppliedTimeUTC, ErrorLevel, Image) + `%ProgramData%\AME\AppliedPlaybooks\` (engine `GetAppliedPlaybooks`).
- Feature request #1702: integrate playbook-update detection into Atlas Toolbox's Update tab (roadmap signal for UltraOS's post-run report).

### 7.3 What happens after a *Windows* feature update (tweak survival)
- **Official Atlas position** (docs https://docs.atlasos.net/faq/general-faq/upgrading-windows-version/): upgrading Windows versions with Atlas applied is **"strongly discouraged and not supported"** — Atlas changes are "specific to the version and build of Windows present during playbook execution"; feature upgrades can cause instability, broken features, **partial or full reversion of tweaks**, or an unusable system. Recommended path: clean reinstall + playbook.
- **Monthly/security updates are fine**: Atlas supports Windows Update since v0.3+ (auto-updates are an opt-out with update *notifications* kept — playbook.conf RadioPage). Docs remedy for WU errors: dism/sfc (§2.1).
- **Mechanics of what needs re-application after a feature update**: (1) deprovisioned-AppX keys don't cover new package versions shipped in the new image → bloat returns (MS docs, §2.2); (2) Windows servicing can restore scheduled tasks (UCPD velocity is pre-disabled by Atlas; EdgeUpdate tasks recreate — #1631) and re-enable services (Atlas pre-disables UCPD service itself to survive, §3.2); (3) registry tweaks mostly survive in-place; (4) component removals (Defender/Teams CABs) **survive** feature updates only until the new image's component store re-adds them — ⚠️ UNVERIFIED for 26H2 specifically (no public Atlas data yet; ReviOS's WinSxS-removal breakage in #49 is the cautionary tale). Practical UltraOS guidance: detect `CurrentBuild` change on next run (store build at apply time) and offer a "re-apply on new build" maintenance pass; ship an Atlas-style `revert.yml` so upgrades from old UltraOS versions cleanly undo past mistakes.
